# WHATWG 规范对抗式审查

将"预设代码是错的"作为审查立场，严格对照 WHATWG 规范条款，逐行核对代码逻辑与规范步骤的一致性。

## 适用场景

- 低参模型生成的代码需要人工校验
- 解析器 / tokenizer / tree construction 等规范密集型模块审查
- 测试失败但无法定位根因时，做全量规范比对
- 合并前合规检查

## 核心铁律

1. **预设代码是错误的** —— 带着"找茬"心态审查，不预设"看起来对就是对"
2. **测试用于检验代码，绝不为了通过测试修改测试** —— 除非能精确引用 WHATWG 章节编号（如 §13.2.6.4.3）证明测试违规，否则任何修改测试的建议无效
3. **逐行核对** —— 不跳读、不概括，每个 match arm 都要找到规范对应条款
4. **不猜** —— 不确定就停下查规范原文，不靠记忆推断

## 审查流程

### 第一步：建立规范锚点

1. 读取 CLAUDE.md / 项目规范，确认参考优先级：**WHATWG > WPT > Chromium 源码**
2. 确认待审查模块对应的规范章节范围（tokenizer = §13.2.5，tree construction = §13.2.6）
3. 准备规范原文，按状态机分支逐个对照

### 第二步：逐状态机分支核对

对每个状态处理函数，按以下 checklist 检查：

#### Checklist A — 分支完整性

- [ ] 规范列出的每个分支（U+XXXX、ASCII alpha、EOF、Anything else）是否都有对应 match arm？
- [ ] 是否有规范未列出但代码自创的分支？（如自创 "SYSTEM" 匹配）
- [ ] `>` / EOF / NULL 等特殊字符是否被正确归入规范定义的分支，而非混入 "anything else"？

#### Checklist B — 步骤一致性

对每个分支，核对规范要求的每一步操作：

- [ ] **状态切换** —— 切到的目标状态是否与规范一致？（如 CommentEndDash vs CommentEnd）
- [ ] **Token 发射** —— 规范要求 emit 的 token 是否被 emit？不要求 emit 的是否误 emit 了？
- [ ] **缓冲区操作** —— append / clear / take 是否与规范一致？
- [ ] **Reconsume** —— 规范要求 reconsume 的是否设置了 reconsume=true？规范不要求的 是否误设了？
- [ ] **Parse error** —— 规范标注 parse error 的位置是否记录了？（至少 TODO 注释）

#### Checklist C — 条件方向

- [ ] 条件判断是否与规范描述**相反**？（如"if buffer == script"写成"!="）
- [ ] 大小写处理是否与规范一致？（ASCII upper → lowercase，ASCII lower → 原样）
- [ ] 字符分类是否正确？（ASCII alphanumeric vs ASCII alpha vs ASCII digit）

#### Checklist D — 内存安全与节点关系

- [ ] `take()` / `mem::take` 是否破坏了规范定义的数据流？（如提前 take 导致后续状态丢失上下文）
- [ ] `Option<TagToken>` 的创建 / 清空时机是否与规范的 token 生命周期一致？
- [ ] `clone()` 是否在规范不允许数据共享的地方引入了意外的数据重复？

### 第三步：交叉验证连锁错误

- [ ] 某状态的 bug 是否会导致下游状态接收到错误的上下文？（如 Bug 8 创建了不该存在的 tag → Bug 6/7 误操作该 tag）
- [ ] 修复一个 bug 后，依赖其错误行为的下游代码是否会暴露新问题？

### 第四步：测试盲区检查

- [ ] 现有测试是否恰好用了规范的特殊分支，"蒙对"了结果却无法暴露 bug？
- [ ] 测试是否断言了**错误**的行为？（即测试本身符合"代码的错误实现"而非规范）
- [ ] 是否需要补充边界用例？（如 `</5` 而非 `</>`，`--!->` 而非 `-->`）

## 高频 Bug 模式（从实战提炼）

以下模式在本项目审查中实际发现，后续审查优先排查：

### 模式 1：特殊字符混入 "anything else"

**症状**：规范对某字符（如 `>`）有独立分支，代码却把它和"anything else"混在一起处理。若"anything else"的行为恰好与该字符的规范行为一致，则`>`"蒙对"，但其他字符全部错误。

**实例**：§13.2.5.7 EndTagOpen，`>` 规范要求只切 Data，"anything else"要求 emit `<`+`/`+reconsume。代码统一"切 Data 不 emit"，`>` 蒙对，其他字符全错。

### 模式 2：发射不该发射的 Token

**症状**：规范只要求切换状态，代码额外 emit 了 token。或规范要求 emit，代码只切状态。

**实例**：§13.2.5.31 ScriptDataDoubleEscapeEnd，规范只切状态，代码 emit 了 `Token::Tag`。

### 模式 3：切错相邻状态

**症状**：状态名相似（CommentEnd / CommentEndDash / CommentEndBang），切到名字像但语义错的状态。

**实例**：§13.2.5.52 CommentEndBang 的 `-` 应切 CommentEndDash，代码切 CommentEnd。

### 模式 4：自创规范没有的逻辑

**症状**：代码添加了规范未定义的匹配 / 回退 / backout 逻辑。

**实例**：§13.2.5.62 BetweenDoctypePublicAndSystemIds 自创 "SYSTEM" 匹配；§13.2.5.31 自创 `script_data_double_escaped_end_tag_name_backout()`。

### 模式 5：缓冲区追加遗漏

**症状**：规范要求 "Append XXX to comment/temp_buffer"，代码忘记追加，导致内容流缺失字符。

**实例**：§13.2.5.48/49 "anything else" 应追加 "<!--" 到 comment，代码直接 reconsume。

### 模式 6：tag/attribute 生命周期错误

**症状**：在规范不要求创建 token 的地方创建了 token，或在该 emit 的时候没 emit。

**实例**：§13.2.5.23 ScriptDataEscapedLessThanSign 不该创建 end tag token，代码创建了；§13.2.5.34 AfterAttributeName "anything else" 应先 emit 当前属性再新建，代码直接 reconsume 导致属性名拼接。

### 模式 7：EOF 处理走捷径丢失 token

**症状**：EOF 时直接设 `eof_emitted=true` 并返回某个 token，跳过了规范要求的 reconsume → 下游状态 emit EOF 的流程，导致 EOF token 丢失。

**实例**：§13.2.5.70 CDATASectionBracket EOF 应 emit `]` + reconsume in CDATASection（后者再 emit EOF），代码直接设 eof_emitted 导致 EOF token 永不发射。

## 输出格式

每个 bug 按以下格式记录：

```markdown
### Bug N — §X.Y.Z 状态名：简述

**位置**：`file.rs:行号`

代码片段。

**规范**：引用规范原文步骤。

**问题**：具体说明代码与规范的差异及后果。
```

最后附优先级表：

```markdown
| 优先级 | Bug # | 影响面 | 修复难度 |
|--------|-------|--------|----------|
| P0     | ...   | ...    | 低/中/高 |
```

## 修复纪律

1. **一次只修一个 bug** —— 不顺手改别的，diff 和任务一样小
2. **先写 failing test** —— 修 bug 前先写一个能暴露 bug 的测试，看它 fail
3. **修 → 看 test pass** —— 修复后测试应变绿
4. **cargo check 零 warning + cargo test 全绿 + cargo fmt 格式化通过** —— 才算修完
5. **连锁检查** —— 修完一个 bug 后，检查是否有依赖其错误行为的下游代码
